## 4. TNV-002：已定位的根因

`HealthCheck()` 在两端都调度 `IncomingVerify()`。该方法通过 `IncomingGet()` 从本地池中消费一个连接，再发送其 ID。对端收到信号后，`OutgoingVerify()` 再用 `OutgoingGet(id)` 消费相应的本地连接。

在一个合法时序中，两端先各自消费了同一个逻辑连接，然后才处理对端的信号。届时该 ID 已从双方本地池移除，且该连接由本地发起的校验关闭；补充的新连接拥有不同 ID，无法补回这次精确 ID 查找。双方等待超时并取消隧道。

失败日志示例（Tunveo WebSocket 第 0001 行）中，双方发起和收到的 ID 都是 `eb712195`，随后都记录 `OutgoingVerify: request timeout`。其他失败使用不同随机 ID，但具有相同的双端关联证据。

这是一项校验连接所有权/发起方向的协议状态问题。它与“先通知 ID、后保存连接”的发布次序风险是两项不同问题，后者尚未单独验证。

### 确定性回归

```sh
go run ./scripts/repro_tls_verify
```

程序使用真实 TLS/TCP 池，先建立并取走控制连接，再只开放一个空闲校验连接；延迟双方信号交付，直到两次本地发起都返回。它调用真实 `IncomingVerify` / `OutgoingVerify`，没有模拟这些方法或替换引擎实现。

测试断言“至少一个校验完成，且两端不被取消”。当前结果恰好相反：同 ID、双方取消、校验 gate 数为 0，退出码 1。Tunveo 与仅替换导入路径的原版各重复 10 次，全部复现：[20 次记录](evidence/m1/tls-verify-reproductions.json)。fixture 将取池超时缩至 100 ms，便于快速回归；上面的未修改二进制仍按原始 5 秒取池超时产生实际故障日志。

下一步应先定义谁发起、谁消费哪一条校验连接，以及取消/关闭的责任，再做最小修复；保留验证业务门槛，不使用跳过校验、延长超时或自动重试作为修复。需要明确旧版本互通的结果，不能仅凭新版本双端通过就宣布兼容。
