# 对齐映射真实调用验证

PR39发现32个未知mmap代次各请求2MiB、各保留1MiB，尚不能由形状判定调用者。本实验在同一冻结PR35 ELF上增加MmapAlignedOrDieOnFatalError及AP32 AllocateBatch的入口、普通RET指令uprobe，验证实际参数、返回、上下文和首尾munmap。无uretprobe、返回地址改写、调用栈扫描或目标内存写入。

## 静态与动态约束

目标ELF SHA256为2b332b9b27afeecca123e2d3fb5819c31bd787406d1393b1335e649a78eec391。对齐函数0x412330/0x196，RET 0x4123fe；AP32函数0x4339a0/0xfb，RET 0x433a2f。每次重建完整反汇编、核对ELF可执行段及RET字节。沿用已验证TracePart CALL/下一指令探针和全内存系统调用记录。

捕获原始TID连续序号、单调时钟、精确exec路径和UID，所有新增上下文也参加完整序号审计。只有在单线程C ABI入口/RET类型及SP严格配对、父上下文闭合、mmap及全部清理严格落在函数内、成功无歧义、返回对齐、首尾裁剪精确覆盖多余区间、返回时仅保留原mmap代次指定区间时才分类。参数必须为不小于页大小的2次幂；不支持的路径阻止后续负载，不猜测。

旧TracePart校验器读取明确标记的去除新增上下文并重新编号的投影；新内存调用/代次和上下文证据恢复原始TID:seq。call_proof字段的序号仍属于投影，不能拿它直接连接原始事件。

控制为4线程各8次已知对齐请求，并由控制程序独立打印TID、size、alignment、pointer，AP父返回也须逐项一致。控制仅验证探测协议，不证明C模拟函数等于sanitizer实现。实际Go路径必须另外观察。

## 执行与失败

先运行控制，再运行两个新进程15秒及180秒负载，配置沿用warmup12秒、每5秒采样、transport3/mode1、workers2/qps10/pool16..64。长窗随后120秒停载、Go scavenge和原observer ACK。沿用原快照、固定预热基线、验证器64MiB预算；资源超限保留失败并允许继续采证，事件/身份/控制/快照失败阻止后续阶段。

沿用PR39 artifact12813365084中实际归档且SHA固定的tracer，而非重新构建后声称字节一致。其来源、CMake、原info与本次ldd/包版本/当前info一并保存；当前bfd=yes、unsafe=no必须通过。Ubuntu24.04运行库不兼容即失败。artifact原始zip校验后仅读取固定名字，目标仍从PR35独立校验恢复。

本阶段不增加pagemap读取；它回答新执行中的实际请求来源和裁剪，不把PR39页观测追认为新执行数据。整VMA RSS仍不能按混合代次比例拆分，也没有观察对象分配/释放、缓存策略或证明泄漏。AP32符号名称、累计虚拟请求和返回范围均不是RSS/PSS或独占物理页量。尚无移除观察器的成对实验。
