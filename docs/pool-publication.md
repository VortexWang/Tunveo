# TNV-003：空闲资源发布与 ID 领取

2026-10-25。本补丁叠加 TNV-013 分支，覆盖四种传输的空闲资源登记，不改变四字节 ID、握手/控制帧或公开构造及获取接口。尚未合并或发布。

## 问题与边界

原实现将空闲资源分为 `sync.Map` 和 ID channel 两份状态。TCP、QUIC、WebSocket 服务端、HTTP/2 两端存在先发送 ID 通知再存入资源的顺序；接收者可能取走通知、发现资源不存在并继续等待，生产者随后留下没有通知的资源。

另外，`OutgoingGet(id)` 从 map 取指定 ID 后，会消费任意一个 channel 元素。先取第二个 ID 时，可能消耗第一个 ID 的通知，随后 FIFO 获取器丢掉第二个已领取 ID 的通知，遗留第一个资源。部分后端的裸 channel 接收还会在删除 map 条目之后无视获取超时而阻塞。仅交换 Store 与通知的顺序不能消除双索引的不一致。

TNV-003 与 TNV-002 的双方 TLS 校验所有权竞争不同，本次不将历史转发失败重新归因于本问题。完整运行代际、旧协程、物理连接替换、重复关闭和重连隔离仍归 TNV-004；HTTP/2 共享物理连接 deadline 仍归 TNV-005。

## 修改

新增内部 `idle.Queue`，用同一互斥锁保护 FIFO 链表和 ID 索引：

- 发布在锁内完成取消/容量/重复 ID 检查，并同时登记资源与次序。返回成功即转移空闲所有权；失败不留下条目，由原调用者关闭资源。
- FIFO 与指定 ID 的领取都在锁内删除同一条目，每个资源只有一个获得者；指定 ID 领取不改变其他 ID 的次序。
- 等待者通过状态变化通知与 context 等待，不使用原来的 50ms 轮询或额外阻塞 channel 接收。截止时间/取消贯穿整个等待；错误包装保留 context 原因。
- `Active` 从同一登记表计算空闲数。`Flush` 原子分离当时的空闲条目，在锁外关闭；已领取资源属于调用者，不被空闲 Flush 关闭。HTTP/2 handler 的闲置清理只移除仍匹配原资源的条目。

四后端两端都使用相同登记表，即使原先“Store 在前”的分支也不再暴露未提交的中间状态。新增模块只使用标准库；第三方依赖、许可证和原始来源校验记录未改变。

`Drain` 不是永久关闭或运行代际屏障。Flush 后的新发布仍可进入队列；尚在建连的旧协程与管理器重启共享状态的隔离问题未由本次解决。不要据此声称整个池生命周期 race-free。

## 可控原生 TCP 复现

`scripts/repro_pool_publication.py` 对指定 Git 提交创建临时归档，只在临时编译副本加入测试调度钩子；生产代码与实际运行二进制不含钩子。测试模板与 runner 的 SHA-256 均记录在结果中。

两个用例各运行十次，调用原生 `handleConnection` / `IncomingGet` / `OutgoingGet`，使用真实回环 TCP socket：

1. 发布窗口：原实现暂停在 ID 发送之后、Store 之前，FIFO getter 超时；新实现暂停在原子发布之后、生产者返回之前，getter 已能领取并通过连接发送数据。
2. 指定 ID：两条连接均完成发布，不暂停任何生产者。先领取第二个 ID，再用 FIFO 领取第一个。原实现稳定超时，新实现保留第一个 ID 并成功领取。
