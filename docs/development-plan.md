# Tunveo 开发与维护计划 V0.2

日期：2026-10-25（北京时间）  
状态：执行计划；尚未完成的事项不代表已经验收。  
依据：仓库基线 `34aaaf04621545dea47d272e72764f8ba621f27f`、[迁移说明](migration.md)、[本地验证记录](validation.md)、[原始诊断结果](forwarding-results.json)。

## 1. 当前目标

在 NodePass v1.17.0 的继承基础上，将 Tunveo 做成可以独立维护、验证和发布的 TCP/UDP 隧道转发工具。近期交付重点是可靠性、安全修复、依赖维护和兼容迁移。

当前以 Go 单仓库、单 module 维护主程序与四个内部池实现。保留 server/client/master 模式及 TCP、QUIC、WebSocket、HTTP/2 传输。近期不增加新的传输协议、管理面板或大规模公共内核重构。

安全扫描和风险分流从第一阶段开始。经确认的高危、紧急漏洞可以立即进入独立修复或依赖安全更新，不必等待全部稳定性工作结束。

## 4. M1：先做可靠复现和安全分流

### 4.1 修整诊断工具

当前 `scripts/verify_forwarding.py` 保留为证据入口，首先补充：

- 分别记录启动、握手、指纹验证、取连接、TCP 回显、UDP 回显和退出阶段；即使 UDP 失败，也保存已经通过的 TCP 结果。
- 每行保存参数、提交、工具链、系统、超时阶段、两端日志和首次失败；中途异常也写出已完成结果。
- 区分就绪等待、业务超时与清理超时。记录重试次数，不能靠增加重试或无限放宽超时把失败变成通过。
- 控制端口争用、进程清理和残留连接，验证诊断工具本身不会造成可避免的误报。
- 为已失败单元格提供定向执行方式，避免每次修改都重复全部矩阵。

先复核原测试条件 `tls=1 / min=2 / max=8`，再增加接近默认配置的对照。先区分测试工具问题、环境问题、原版已有问题和迁移引入问题，再确定代码修复位置。

### 4.2 建立缺陷台账

每项记录：编号、现象、证据链接、复现条件、影响面、根因状态、优先级、修复提交、回归用例、兼容影响及剩余风险。状态使用“待验证／已复现／已定位／已修复待验收／已验收”；不能凭代码阅读直接标记漏洞已确认或已关闭。

### 4.3 同步做首轮安全扫描

对当前精确基线执行模块校验、`govulncheck` 与源码排查，记录扫描器版本、漏洞库时间、目标平台、实际可达调用和补丁版本。区分标准库、第三方模块和内置源码；四库内置后，原模块的版本漏洞匹配不能替代人工公告与源码跟踪。

扫描命中不直接等于可利用，扫描无命中不等于安全。确认紧急风险后单独修复，安全依赖更新可以提前进入 M4 的分批流程。

## 6. M2/M3：修复方式和必须覆盖的行为

每个补丁尽量对应一个根因：先加入能触发问题的用例，再做最小修复，再验证受影响的传输及新旧互通。建立实际运行的 Go 测试；只执行没有用例的 `go test -race` 不计入并发验收。

重点验证：

- 连接、流和控制通道的所有权及消费规则；验证连接不能被双方以冲突方式取走，失败也不能默默放行业务。
- 初始化、取消、重连、Flush、Close、重复关闭的边界；处理进行中的握手和 I/O，确保等待可结束、资源可回收。
- HTTP/2 与 QUIC 的单流关闭、读写截止时间、双向取消及共享连接故障影响范围。
- TCP 具体类型断言的有效前提；对不满足前提的连接给出可控错误。
- 严格 TLS 的证书错误、SNI/主机名不匹配、过期证书、加载失败和轮换；区分初始加载失败与运行时换证失败。
- 模式 1 的现有指纹比较和整个握手信任边界。即使当前比较通过，也不能将其描述为已认证的安全信道；需要安全设计评审。
- URL 口令、API Key、日志、状态文件、配置导出中的秘密保护；避免在管理响应中无意暴露凭据。
- 管理 API、MCP、SSE 与实例操作的鉴权、输入限制、超时、资源上限和进程清理。

安全修复可能需要改变旧行为，例如拒绝证书错误时继续启动。这类变更必须列明影响及迁移方式，不以“兼容”为由保留隐式安全降级，也不在未验证前重写协议或加密方案。

## 8. 验收和发布门槛

### 8.1 测试矩阵

矩阵维度包括：四种池传输、两种流向、TCP/UDP 业务、各传输实际支持的 TLS 模式、Tunveo 双端和两个新旧混合方向，以及最小/小容量/默认连接池配置。无效配置应明确拒绝；不支持的组合记录原因，不能标成通过。

先用定向最小用例定位，再做受影响矩阵回归；阶段验收及发布候选再执行完整支持矩阵。

初始验收目标：

- 每个声明支持的功能单元格连续运行至少 10 轮，零未解释失败；失败必须有台账，不以重试后成功替代结果。
- 每种传输覆盖至少 100 次建立/断开和实例启停，所有测试有期限并完成清理；记录 goroutine、FD 和内存回落情况。
- 发布候选阶段，每种传输在明确并发数、业务比例、机器配置及负载下连续运行至少 24 小时；资源没有无法解释的持续增长。
- 关键并发路径有实际执行的 race 测试，且测试终止、取消及错误路径，不仅检查正常回显。

这些是项目验收门槛，不是已经达到的性能指标；如运行证据显示门槛需调整，要记录原因与替代证据。

### 8.2 兼容及运维

验证 URL/CLI、管理 API/MCP、环境变量、状态和配置导入导出。`NP_*` 保持现有兼容；如增加 `TUNVEO_*`，单独定义优先级、冲突与废弃策略并测试。不得静默丢弃旧配置。

对 `nodepass.gob` 到 `tunveo.gob` 的迁移，提供受控样本、离线备份、转换/导入流程、失败检测和回滚说明；没有验证前不承诺直接复制即可兼容。

平台表分别列出“可交叉编译”“有原生运行证据”和“正式支持”。Docker、GoReleaser、归档许可证、版本输出及校验和必须验收；编译成功不能冒充原生验收。

### 8.3 版本节奏

- `v0.1.0-alpha.1`：用于验证的预发行，完成第一批确定性修复并明确剩余限制。
- `v0.1.0-beta.1`：核心稳定性、安全与依赖升级回归达到对应门槛，用于迁移和较长周期验证。
- `v0.1.0`：所有对外声明支持的范围通过发布验收；已确认紧急/高危安全项及关键数据正确性、崩溃、死锁问题关闭。

版本名是规划，未创建这些标签。每次发布附已知问题、兼容变化、精确依赖、SBOM/许可证、安装与回滚说明。没有经过验证的平台或功能缩减支持范围并明确说明，不用扩大宣传替代验收。

## 9. 提交与维护规则

主分支当前是开发基线。后续代码修复使用任务分支和 PR，按根因分别评审；计划和验证文档随事实更新。分开提交迁移、修复、依赖更新、行为变更与重构。

CI 保留编译/静态检查和实际转发检查的独立结果。不得关闭失败检查或使用 `continue-on-error` 来制造通过。文档改动本身不需要重复本地运行完整转发矩阵；实现修改后先执行与影响范围相称的检查。

变更四库内置实现时，更新本地修改记录，保留原始导入哈希供追溯，不能用修改后的哈希覆盖原始证据。确认的安全问题按 SECURITY.md 处理；对外披露前避免公开真实凭据或可直接利用的未修复细节。

M6 的公共逻辑抽取只在重复行为已有测试之后推进；TCP、WebSocket、QUIC 和 HTTP/2 的流生命周期不同，不为了统一接口强行合并资源所有权。

## 10. 下一步的具体交付

首个实施任务为 **TNV-001 + TNV-002 的定位准备**：

1. 完善诊断的分阶段结果、定向运行和失败证据保存。
2. 选取 `type=2 / mode=1 / tls=1` 与 `type=1 / mode=2 / tls=1` 两个已失败单元格，复核原版和 Tunveo 的真实失败位置，并加入默认容量对照。
3. 为首个确认根因建立最小、可重复、有限时的回归测试，确定最小修复范围。
4. 同步形成首轮漏洞扫描及安全分流记录，优先验证 TLS 降级和日志口令问题。

这一步交付复现证据、首个回归用例及缺陷优先级；不预先承诺某一猜测就是根因，也不在定位前启动大规模重构或全量依赖升级。
