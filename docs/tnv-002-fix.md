# TNV-002 修复记录

2026-10-25。本次修复 TLS 校验时双方抢占同一连接池 ID 的问题，并修复新服务端握手响应尚未刷新即切换监听器导致的早期 EOF。PR #2 叠加在 M1 诊断 PR #1 上；本记录不表示已经合并或发布。

## 行为变化

新端通过 HTTPS 请求头与响应字段协商 `flow-v1`。双方都支持时，mode=1 由客户端发起，mode=2 由服务端发起；对端验证指纹并发送匹配 ID/指纹的 ACK，发起端收到 ACK 后完成校验。重复消息幂等，错误消息、超时与取消不能打开业务门闩。

与原版 v1.17.0 配对时，新端先响应旧端校验，再使用另一连接 ID 发起原协议校验，不向旧端发送 ACK 扩展。每轮运行拥有独立状态，延迟回调捕获该轮状态；完整重启和池生命周期问题仍属于 TNV-004。详细协议见 [TLS 校验协议](tls-verification.md)。

握手 HTTP 响应设置 Content-Length 并完整写入、刷新后，才切换监听器。此修改只覆盖新服务端；不声称修复旧服务端的所有 EOF 原因。

## 首轮失败与证据完整性

首轮矩阵保留原有结果：45 个通过，3 个在证书校验阶段超时（新/新 QUIC mode=2 小池、新/旧 WS mode=1 小池、旧/新 H2 mode=2 默认池）。这些记录存在阶段已观察到的日志里程碑在最终日志中缺失的不一致，原因尚未归属，不能据此判定引擎成功或环境故障。

因此驱动改为父进程通过管道单次读取，先写入脱敏日志，再追加到阶段快照；记录驱动 SHA-256 和阶段日志字节数。之后重新执行完整 48 格矩阵全部通过。首轮失败没有改写为通过，M1 原始失败证据也保持不变。

完整报告、初轮及最终全部日志、真实池复现结果和逐文件 SHA-256 清单位于 [evidence/tnv002](evidence/tnv002)。路径仅作可移植化：日志路径相对各自报告，二进制路径记为 `BUILD/`；日志字节和结果保持不变。
