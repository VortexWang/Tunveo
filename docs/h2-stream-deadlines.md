# TNV-005 HTTP/2 单流期限与取消

2026-10-25。PR #9 叠加于 TNV-004 的 PR #8，尚未合并或发布。

## 确认的问题

旧 StreamConn.SetDeadline / SetReadDeadline / SetWriteDeadline 修改共享 TLS 连接。对一个逻辑流设置读期限，可能使同一物理连接上的其他流一起断开；而写入已停在 HTTP/2 流控窗口上时，物理 socket 的写期限又不能可靠唤醒它。

原生测试通过实际 Pool 建立 TLS/HTTP2 连接，在同一物理连接上领取两个逻辑流；分别测试客户端和服务端的读、写期限。相同模板在父提交 `fedae8e4da5c3f9c01a7bce4573157417a483f7e` 运行，预期缺陷的开关只存在于测试代码，生产源码没有插桩。读/写 × 两端 × 十轮的结果见证据目录。测试不是现场故障率估计。

## 修复后的契约

期限现在只作用于逻辑流的 deadlineIO，不访问物理连接。内部用两对 net.Pipe 提供独立的读写期限；清除或延长期限能够作用于正在等待的调用。超时返回可由 errors.Is(err, os.ErrDeadlineExceeded) 识别的错误，不自动关闭流或取消整个 HTTP/2 连接。清除期限后可以继续使用该流。

每个方向首次使用时才启动一个 I/O 泵，最多两个泵、各一个 32 KiB 工作缓冲；空闲流不预先启动泵。此处的有界工作缓冲不包含 x/net/http2 自身的流控与协议缓冲。

Write 串行提交至多 32 KiB 的片段。成功返回前，片段必须完成底层流写入；服务端响应还必须完成 Flush，避免发送校验 ACK 后立即 Close 丢失本地尚未提交的数据。这是本地工作线程的完成确认，不新增线上 ACK 或协议字段。超时允许返回已接受的部分字节数，这些数据可能仍在当前片段中等待 HTTP/2 流控；恢复后先完成这个片段的确认，再接受新的写入，防止错位或重复。

Close 先唤醒本地读写和泵，再终止对应 HTTP/2 请求/响应，等待已启动的泵退出。客户端响应头返回后的请求取消也显式关闭该逻辑流，释放仍被请求体读写阻塞的任务。服务端关闭使用已有的单流响应写中断机制，不触碰共享 TLS socket 的期限。关闭一个流不关闭兄弟流；物理连接被远端关闭或 Pool.Close 时，全部相关流仍会终止。

## 验证方式与边界

读测试在调用已经等待时设置期限，断言超时、兄弟流双向传输、清除期限后原流恢复，并检查没有增加物理 accept。写测试先让对端收到一个字节，确认已进入真实 I/O，再设期限；其余数据超过 HTTP/2 的流控窗口。断言部分字节计数及超时，排空接受的数据后原流恢复，且物理连接不变。

HTTP/2 流仍共享连接级流控。流 A 耗尽连接窗口时，同方向的 B 可能自然背压；期限隔离不是带宽或流控隔离。测试先检查 B 的独立反方向，排空 A 后再检查 B 双向，避免将协议背压归为共享 socket 期限缺陷。没有增加连接窗口、取消协议背压或掩盖失败。

额外回归覆盖延长期限替换旧定时器、同时设置/清除读写期限、Close 唤醒并回收阻塞泵、成功 Write 后立即关闭不丢 ACK，以及客户端关闭、服务端关闭和请求取消后的兄弟流可用性。

开发中间态的失败记录也保留：初始本地适配层的请求取消未释放阻塞读取；早期测试将 16 MiB 分配计入期限，或在 I/O 起点前超时。最终测试把大缓冲分配放在工作协程外，并在收到真实首字节后计时；未增加期限、重试业务回显或覆盖原失败报告。
